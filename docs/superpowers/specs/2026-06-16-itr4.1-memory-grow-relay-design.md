# itr 4.1 — Coproc Memory Grow + Extensible Re-lay (Design Spec)

Date: 2026-06-16
Status: approved in brainstorm
Scope: foundational memory work BEFORE itr 4 (world events). Removes the
coproc code ceiling and re-lays SDRAM so future content (more crops,
recipes, goods, plots, fields) never forces another layout migration.

## Goal

Stop treating coproc memory as a constraint when designing features. Three
moves, one increment:

1. **Grow coproc BRAM 16 → 48 KB** (gateware) — removes the executable-code
   ceiling. Code runs only from BRAM; 48 KB gives 40 KB of contiguous task
   space.
2. **Repack the BRAM map** — generous, clearly-bounded per-task regions with
   room for future tasks; one shared scratch region. No tight caps.
3. **Re-lay the SDRAM banks to MAX-sized fixed regions** — reserve room for
   `NCROPS_MAX`/`NRECIP_MAX` (not today's live counts) so growing a count up
   to its MAX is zero layout change, zero migration. The 2-byte plot
   encoding removes the per-plot data ceiling. Multi-field is reserved as a
   bank-per-field convention (documented, not built).

This is paid once: one gateware flash, one CVER=4 migration. After it,
content growth is "bump a live-count constant," never a re-lay.

## Key principle (the whole point)

**Count ≠ layout.** Today every count (`NCROPS=4`, `NRECIP=12`) is also a
layout constant, so bumping it shifts every following field and forces a
migration. After this re-lay, SDRAM offsets are static and sized to a MAX;
the live count only says "how many slots are active." SDRAM is 64 MB —
reserving generously is free. The only cost is the one-time migration here.

Locked MAXes: `NCROPS_MAX=16`, `NRECIP_MAX=64` (so `NGOODS_MAX=64`, DISC
bitmap 8 bytes = 64 bits), `NSTATIONS_MAX=4`. Live today: NCROPS=4,
NRECIP=12, NSTATIONS=2.

`NGOODS_MAX = NRECIP_MAX` is a deliberate coupling, not a coincidence: one
good per recipe (a recipe produces its product). If goods ever decouple from
recipes (e.g., a good not tied to a recipe), GOODS[64]/DISC[8] would re-lay —
acceptable, and the only foreseen reason to revisit these two regions.

## §1 — Gateware: BRAM 16 → 48 KB

`gateware/rev2/project_obscurus/coproc.v` — same edit pattern proven in the
8 → 16 grow:

**`coproc.v`:**
- `reg [7:0] bram [0:49151]` (48 KB).
- `in_bram = ~(AB[15] & AB[14])` → $0000-$BFFF (everything below the $C000
  quadrant). $C000-$DFFF unused; the $E000-$E0xx I/O window is special-cased
  ABOVE this decode (unchanged), $FFFx vectors unchanged.
- **`laddr` input → `[15:0]`; Arlet `wr_addr` → `AB[15:0]`** (currently
  `AB[13:0]` — leave it 14-bit and Arlet writes above $3FFF alias). Port-B
  reads `bram[laddr[15:0]]`; port-A `bram_qa <= bram[AB[15:0]]`.
- **Write-protect slices widen from 14-bit to 16-bit, same regions:** kernel
  $1000-$1FFF → `AB[15:12]==4'h1` (was `AB[13:12]==2'b01`) for `a_wr_ok` and
  `laddr[15:12]==4'h1` for `b_wr_ok`; TABLE $0200-$02FF →
  `AB[15:8]==8'h02` (was `AB[13:8]==6'h02`). Same protected regions, just
  decoded across the wider address.

**`project_obscurus_top.v` — the load-address path (THIS is the edit that
actually unlocks $4000-$BFFF; widening BRAM alone is not enough):**
- `m_laddr`: declaration `[13:0]` → `[15:0]`; reset `13'd0` → `16'd0`.
- **CP_LADDR_HI capture (line ~424): `m_laddr[13:8] <= wr_data_latch[5:0]`
  → `m_laddr[15:8] <= wr_data_latch[7:0]`.** Currently only 6 high bits are
  captured → max reachable load address is $3FFF → WORKTASK@$4000 (and every
  task above $3FFF) would silently fail to load. This single mask is the
  unlock. Update the CP_LADDR_HI doc comment ("high 6 bits of 14-bit" →
  "high 8 bits of 16-bit") too.
- `cp_laddr_mux`: `[13:0]` → `[15:0]`; the cflash zero-extends widen
  `{1'b0, rst_laddr}` / `{1'b0, save_laddr}` → `{3'b0, ...}` (the cflash
  engines stay 13-bit — see snapshot-coverage note in §2).
- Synth + PNR must stay clean; fmax has ~8× margin so the larger BRAM
  (~24 × DP16KD of the ECP5's ~208) is no timing concern.
- **Requires an FPGA reflash.** Bundle with itr 4's first flash if desired;
  sim gates everything first.

## §2 — BRAM repack (48 KB map)

**32 KB of task code** at $2000-$9FFF (4 × 8 KB regions) + 4 KB shared
scratch ($A000) + 4 KB spare ($B000) = 40 KB total in the $2000-$BFFF span.
Generous per-task regions, room for the vendor/mission tasks the roadmap
implies, one shared scratch.

| Region | Use |
|---|---|
| $0000-$00FF | ZP (kernel + TCB) — unchanged |
| $0100-$01FF | stacks — unchanged |
| $0200-$02FF | TABLE (write-protected) — unchanged |
| $0F80-$0FFF | kernel mailboxes — unchanged |
| $1000-$1FFF | kernel (write-protected; IRQ/NMI $1F00/$1F40) — unchanged |
| $2000-$3FFF | FARMTASK code (8 KB; was $0600, ~1.7 KB) |
| $4000-$5FFF | WORKTASK code (8 KB; was $2000, ~1.3 KB) |
| $6000-$7FFF | future task 3 (reserved) |
| $8000-$9FFF | future task 4 (reserved) |
| $A000-$AFFF | shared task scratch (all tasks; EVLIB + per-task vars) |
| $B000-$BFFF | spare |

Consequences:
- **FARMTASK relocates** $0600 → $2000: its `ORG`, the //e `LOADF`/TABLE[2]
  vector ($0204 = $00,$20), and the FARMTASK_MAXLEN cap (now 8 KB) change.
- **WORKTASK relocates** $2000 → $4000: its `ORG`, the //e `LOADW`/TABLE[3]
  vector ($0206 = $00,$40), and WORKTASK_MAXLEN (8 KB).
- **Scratch moves to $A000+**: FARMTASK scratch (currently $0E00), WORKTASK
  scratch ($0D00), and the EVLIB scratch (per-includer) relocate into the
  $A000 page. This dissolves the old $0D00-cap-on-FARMTASK problem entirely
  — tasks no longer collide with scratch.
- The old low region $0300-$0F7F becomes free/unused (Conway demo aside).

**Snapshot-coverage regression (stated, not a farm-game problem):** the
cflash save/restore engines are 13-bit — they cover only $0200-$0FFF. Today
task scratch sits at $0D00/$0E00, INSIDE that window, so a snapshot captures
it. After this repack, BOTH task code ($2000+) AND task scratch ($A000) are
OUTSIDE the snapshot window — the cflash snapshot will capture ONLY the low
region (ZP, stacks, TABLE, kernel mailboxes), i.e. **zero task code and zero
task scratch.** This is fine for the farm game, which uses the **respawn**
model (//e streams the blobs fresh; scratch — GTICK, decay/market counters,
LFSR state — resets on respawn anyway, and the farm already tolerates that).
It is a real limitation ONLY for the hypervisor suspend/resume feature
(separate, not built for the farm tasks): to snapshot these tasks seamlessly,
the cflash save/restore engines would have to widen to 16-bit to cover
$2000-$BFFF. Flagged here so that future feature owns the widening; this
increment does not need it.

## §3 — SDRAM re-lay (MAX-sized)

### Bank 32 (farm) — NCROPS_MAX=16

| Addr | Content |
|---|---|
| $0000-$0001 | SIG ("FM") |
| $0002 / $0003 | SEQCTR / HEAD |
| $0004 | HBEAT |
| $0005 | CVER (=4) |
| $0006-$000F | event state (day counter, active event id, days-left, news id) — reserved for itr 4 |
| $0100-$01FF | RING 64×4 (page-aligned) |
| $0200-$0207 | MAILBOX(8) |
| $0210-$023F | MARKET: 16 × (PRICE lo, PRICE hi, SUPPLY) = 48 B |
| $0240-$0241 | CASH lo/hi |
| $0242-$0251 | FSEEDS[16] |
| $0252-$0261 | FCROPS[16] |
| $0300-$061F | GRID: 2-byte plots × 400 = 800 B ($320) |

### Bank 33 (workshop) — NRECIP_MAX=64

| Addr | Content |
|---|---|
| $0000-$0001 | SIG ("WK") |
| $0002 / $0003 | SEQCTR / HEAD |
| $0004 | HBEAT |
| $0005 | CVER (=4) |
| $0100-$01FF | RING 64×4 (page-aligned) |
| $0200-$0207 | MAILBOX(8) |
| $0210 | SKILL |
| $0211-$0218 | DISC bitmap (8 B = 64 recipes) |
| $0219 | MODE (bit0 BOOM) |
| $0220-$022F | STATIONS: 4 × 4 B (NSTATIONS_MAX=4) |
| $0240-$027F | GOODS[64] |
| $0300-$04FF | RECIPES: 64 × 8 (//e-seeded) |

All array bases are fixed. Per-crop/recipe/good offset = base + index×width,
computed from the index against the MAX-sized region. The live count
(NCROPS/NRECIP/NSTATIONS) only bounds loops and validation — it is NOT a
layout constant. Bumping a live count up to its MAX requires NO address
change and NO migration.

## §4 — Plot encoding: 2 bytes

Each plot is 2 bytes:
- **Byte 0 = crop id** (0-15).
- **Byte 1 = stage + flags:** low nibble = stage (0 empty, 1-5 grow, 6 ripe,
  7 dead, **8-15 reserved** for future growth stages); high nibble = flags
  (bit 4 watered, bit 5 fertilized, bit 6 blighted, bit 7 reserved).
- Empty plot = stage nibble 0 (crop byte irrelevant when empty; harvest/clear
  writes both bytes 0). **Render MUST gate on stage first:** read the stage
  nibble, and if empty (0) draw the empty cell WITHOUT reading crop→color —
  else a stale crop byte under an empty plot flashes a phantom color. (Same
  ordering DOGROW uses: skip empty before decoding crop.)
- `PLOTADR = FGRID + 2 × (y×20 + x)`. `DOGROW` walks the grid stepping by 2.
  Render reads both bytes (crop → color, stage → fill). The stage/flags
  split lets itr 4 (blight, irrigation, soil) and beyond add per-plot state
  with no further migration.

This touches FARMTASK (CPLANT/CHARV/DOGROW/PLOTADR/DOMKT crop indexing) and
FARM.S (PLOTDRAW/render, SHADOW now 800 B, RDGRID/DRAWALL, COLDST grid init).
The //e SHADOW buffer doubles to 800 B (fine — //e has ~17 KB free
post-relocate).

## §5 — Multi-field: convention, not built

Bank 32 is laid as ONE field, cleanly and page-friendly. Future fields are
**additional SDRAM banks 34, 35, … each laid identically to bank 32.**
Single-writer-per-bank stays clean; a field could be its own coproc task.
This increment does NOT build multi-field — it only documents the convention
so adding a field later is "seed bank 34, spawn a task," with zero re-lay of
bank 32. NPLOTS per field stays 400 (20×20) for now.

## §6 — Migration: full re-seed (CVER=4)

The re-lay moves every SDRAM field, so a field-by-field 3→4 migration would
be fragile hand-mapping. Instead **CVER=4 = full cold-seed of BOTH banks**:
crops, cash, seeds, market, grid, skill, recipes, goods, stations all reset
to fresh. The current bench world (and discovered recipes + skill) is lost
**one time** — accepted, because this is the foundational last-big-layout
change and the world has been re-seeded throughout development anyway.

After this, the MAX-sized layout means content growth never migrates again —
this is the final CVER bump for layout reasons. (Future CVER bumps, if any,
would be for genuinely new bank regions, not resizing existing ones.)

Deploy: **flash the 48 KB bitstream, then BRUN.** Both blobs reload at their
new ORGs; both banks cold-seed (invalid/old SIG or CVER mismatch → full
seed). World starts fresh.

## Testing

- Gateware: full sim suite green at 48 KB BRAM; confirm tasks load/run at
  the new ORGs ($2000 farm, $4000 workshop), kernel/TABLE protects hold at
  the widened range, host loader writes the full $0000-$BFFF except kernel.
- A focused tb phase: load a byte to $4000-$BFFF via the host port and read
  it back (proves the new BRAM range is real + writable).
- SDRAM re-lay: tb asserts every relocated field at its new address
  (market, cash, seeds[16], crops[16], grid 2-byte, skill, disc[8],
  goods[64], stations[4], recipes[64]); plot ops (plant/harvest/grow) on the
  2-byte encoding; a NCROPS=8 / NRECIP=24 smoke (bump live counts, confirm
  no overflow into neighbors — proves MAX headroom).
- Migration: CVER mismatch / cold start → full seed; assert all regions
  initialized.
- Stale-artifact guard (the recurring lesson): force-clean rebuild, verify
  embeds == bins, .bin sizes reflect the new ORGs, blob load-addresses on
  disk match, and the gateware bitstream is freshly synthesized — sim-green
  ≠ hardware-current.

## Out of scope (later increments)

- World events (itr 4) — authored AGAINST this roomy layout; the event-state
  bytes ($0006-$000F bank 32) + per-plot flags are reserved here for it.
- Multi-field implementation, vendor/mission tasks — use the reserved BRAM
  task regions ($6000/$8000) and bank-per-field convention.
- Growing past a MAX (NCROPS>16, NRECIP>64) — not expected; would be the
  only thing forcing a future re-lay.
